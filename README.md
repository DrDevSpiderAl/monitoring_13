

## Домашняя работа к занятию «13.Системы мониторинга»

1.  В данном случае необходим следующий набор метрик:
a.  ЦПУ, а именно: Utilization (node_cpu_seconds_total) и Saturation (node_load1...и другие) для анализа загрузки ЦПУ и очереди задач, ожидающих обработку на ЦПУ
б.  http метрики, а именно: контроль потока HTTP-запросов и расчёта доли ошибок (http_requests_total), контроль времени ответа сервиса и выявления деградации производительности (http_request_duration_seconds) и вычислять из отношение из числа запросов завершившихся ошибками к общему числу запросов.
в.  Метрики на диски, на которых сохраняются текстовые отчеты, а именно: контроль свободного места на диске (node_filesystem_avail_bytes, node_filesystem_size_bytes), контроль занятости дисковой подсистемы (node_disk_io_time_seconds_total)

2.  Я предложу перевести технический мониторинг на язык бизнеса с помощью концепции SLI / SLO (Service Level Indicators / Objectives) и собрать для него Executive Dashboard (дашборд для менеджмента).
Возможный набор SLI/SLO:
Availability SLI (доступность сервиса, успешные HTTP-запросы)/(все HTTP-запросы) - пример результата: 99.9% успешных запросов за 30 дней
Latency SLI (скорость отклика в доле запросов быстрее заданного времени). Например отклик 95% запросов быстрее 1 секунды за 30 дней
Report success SLI (доля запросов, завершившихся успешно). Например 99.5% успешных отчётов за 30 дней.
Этот подход поможет бизнезу определить насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания.

3. В условиях ограниченного финансирование на построение системы сбора логов, можно воспользоваться Open Source инструменты и перенести акцент с хранения всех логов на сбор и доставку конкретных ошибок.
Например поставить Sentry через docker которая будет собирать ошибки в приложение и направлять аллерты на почту или в tg bot.
Можно сделать отдельные кастомные логеры на уровне приложений и тоже направлять их на почту или tg bot.

4. Ошибка в том, что в формуле успешными считаются только ответы с кодами 2xx, хотя для HTTP-сервиса нормальными и корректными могут быть и ответы 3xx, например редиректы или 304 Not Modified. Если в системе нет 4xx и 5xx, а показатель SLA не поднимается выше 70%, значит значительная часть запросов возвращается с кодами 3xx и ошибочно считается неуспешной. Следовательно, ошибка находится в формуле расчёта SLA и в неверной классификации HTTP-кодов ответов. Корректнее считать SLA по формуле (2xx + 3xx) / all_valid_requests

5. Основные плюсы push-модели:
- упрощенние репликации данных в разные системы мониторинга или их резервные копии
- более гибкая настройка отправки пакетов данных с метриками
- использование UDP, которое является менее затратным способом передачи данных, как следствие врзрастает производительность сбора метрик
Минусы push-модели:
- существует риск перегрузки сервера (Push Storm)
- сложнее обнаружить падение сервиса в случае если приложение "зависло" или "упало", оно просто перестает слать метрики

Основные плюсы pull-модели:
- проще обнаружить падение сервиса в случае если приложение "зависло" или "упало", сразу видно что узел перестал отвечать
- упрощенная отладка получения данных с агентов
- можно настроить единый proxy server до всех агентов с TLS
- легко контролировать подлинность данных
Минусы pull-модели:
- если программа работает очень недолго и завершается раньше следующего опроса, мониторинг может вообще не успеть снять с неё метрики при неверных настройках таймингов
- при большом количестве целей сервер мониторинга нужно грамотно масштабировать, чтобы он успевал всех опрашивать
- сложность работы за NAT / Dynamic IP / Serverless

6. Prometheus относится в основном к pull-модели
TICK (Telegraf + InfluxDB + Chronograf + Kapacitor) обычно относят к push-модели
Zabbix является гибридной системой, так как поддерживает и пассивные проверки, где сервер сам опрашивает агент, и активные, где агент сам отправляет данные.
VictoriaMetrics также можно считать гибридной системой.
Nagios тоже относится к гибридным системам, поскольку поддерживает активные и пассивные проверки.
